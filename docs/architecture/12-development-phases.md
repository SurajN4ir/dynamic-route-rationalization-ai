# 12. Development Phases & Acceptance Criteria

Each phase has an entry condition (what must already be true) and an exit
condition (what must be demonstrably working before starting the next
phase). Exit conditions should be checkable, not vibes — link to the
specific FR/NFR ids they satisfy.

## Phase 0 — Architecture (current)

- **Entry:** none.
- **Exit:** docs 01-15 committed and internally consistent (no contradiction
  between the data model, API spec, and RL spec). This document set.

## Phase 1 — Infrastructure

- **Entry:** Phase 0 exit.
- **Build:** `docker-compose.yml` (doc 11), Postgres+PostGIS, Redis, empty
  FastAPI service skeletons for all six services (doc 10), empty Next.js
  app, CI pipeline skeleton, structured logging, `.env` handling.
- **Exit:** `docker-compose up` brings up all services healthy; each
  service responds on `/healthz`; CI runs (even if there's nothing to test
  yet beyond lint).

## Phase 2 — Transportation foundation

- **Entry:** Phase 1 exit.
- **Build, staged as three tasks** (split during implementation — see
  [PHASE2_DESIGN.md](PHASE2_DESIGN.md) / [TASK202_DESIGN.md](TASK202_DESIGN.md)):
  - **TASK-201 (done):** the persisted domain/spatial foundation —
    `intersections`/`roads`/`road_segments` (the physical road network;
    **PostGIS is the system of record here, not the osmnx graph** — a
    clarification of this section's original "road graph via osmnx"
    phrasing, decided during TASK-201), plus `stops`/`routes`/
    `route_stops`/`vehicles` (extended with source-tracking columns) and
    two new tables, `service_calendars`/`vehicle_assignments`. Read-only
    `/api/v1/{roads,stops,routes,vehicles}` endpoints. No OSM ingestion,
    no in-memory graph construction, no routing algorithm yet — deliberately
    out of scope for TASK-201.
  - **TASK-202 (done):** a deterministic, idempotent OSM XML ingestion
    pipeline (FR-INGEST-04, for a bounded/representative extract) that
    populates TASK-201's schema — parse/validate/normalize/derive-topology/
    persist, with a CLI entry point, dry-run mode, and full test coverage
    against a real PostGIS database. Required one corrective migration
    (`0003`) to `road_segments`'/`roads`' uniqueness constraints — see
    TASK202_DESIGN.md §1. No in-memory graph construction, no routing
    algorithm — deliberately out of scope for TASK-202.
  - **TASK-203 (not started):** in-memory NetworkX/OSMnx graph construction
    *derived from* the now-populated canonical schema, and basic
    A*/Dijkstra routing over that graph.
- **Exit:** given two points on the network, the routing service returns a
  valid path (TASK-203); static route/stop data for the demo network is
  queryable via `/routes`, `/routes/{id}/stops` (TASK-201, done).

## Phase 3 — Real-time engine

- **Entry:** Phase 2 exit.
- **Build:** telemetry API (FR-INGEST-01/02/06), phone telemetry client,
  SUMO telemetry bridge (doc 09 §9.6), Redis Streams pipeline, fused state
  cache, WebSocket fan-out, live map in `apps/web`.
- **Exit:** at least 1 phone + a SUMO-simulated fleet both show up moving on
  the live map within the NFR-02.1 latency targets.

## Phase 4 — Prediction

- **Entry:** Phase 3 exit (need real telemetry stream + historical data to train against).
  **Historical data sourcing is not yet decided** (see architecture review)
  — the default assumption is that "historical" training data for the
  demo network is generated by running many extended, varied-seed SUMO
  simulations (doc 09 §9.3) rather than assuming a real historical transit
  dataset exists for whatever city is chosen; a real public GTFS/GTFS-RT
  archive is used opportunistically if one is actually obtainable for free,
  but the plan must not depend on it existing.
- **Build:** all five models (doc 07) at least at their first baseline tier
  (historical average / naive), served via `services/prediction`.
- **Exit:** `/predictions/*` endpoints return real (not mocked) predictions
  for the demo network; each model has a recorded baseline metric (doc 14).

## Phase 5 — Decision engine

- **Entry:** Phase 4 exit.
- **Build:** rule engine (FR-DEC-02), constraint validator + action masking
  (doc 08.3), route/graph engine integration for `REROUTE_BUS` feasibility.
- **Exit:** given a synthetic bunching/delay scenario, the rule-based
  controller produces a valid, constraint-passing candidate action.

## Phase 6 — Reinforcement learning

- **Entry:** Phase 5 exit (need constraint engine for action masking) + Phase 9's
  SUMO integration groundwork pulled forward as needed (network + scenario
  library must exist before training, so parts of doc 09 §9.2-9.3 land here
  in practice even though "digital twin" is nominally Phase 7).
- **Build:** `AuraEnv` (doc 09 §9.5), reward function (doc 08.4) with
  configurable weights, DQN agent, PPO agent, training runs logged to
  MLflow.
- **Exit:** DQN and PPO both train to a stable policy on at least the
  `normal` and one disruption scenario; each beats the fixed-timetable
  baseline on the primary reward components in evaluation (doc 14).

## Phase 7 — Digital twin (counterfactual engine)

- **Entry:** Phase 6 exit (SUMO bridge already exists from Phase 6; this
  phase is about exposing it for *human-facing* what-if comparisons, FR-SIM-01).
- **Build:** `/recommendations/{id}/simulate` and `/simulation/scenarios/{name}/run`
  endpoints, parallel candidate-action evaluation, `simulation_results` persistence.
- **Exit:** for a live-detected bunching event, the system can simulate all
  candidate actions and return comparative outcome metrics within the
  NFR-02.1 time budget.

## Phase 8 — Recommendation system

- **Entry:** Phase 7 exit.
- **Build:** ranking + explanation generation (FR-REC-01), controller
  approve/reject flow (FR-REC-02) with audit logging, outcome feedback
  linkage (FR-REC-03).
- **Exit:** end-to-end demo path works: detected risk → RL candidate →
  simulated → ranked recommendation with explanation → controller approves
  in `apps/web` → audit log entry created.

## Phase 9 — Route rationalization

- **Entry:** Phase 8 exit + enough accumulated historical/demo data to
  compute meaningful utilization stats.
- **Build:** utilization/overlap/coverage analytics (FR-ROUTE-01), frequency
  recommendation logic (FR-ROUTE-02).
- **Exit:** `/analytics/routes/{id}/recommendations` produces a plausible
  frequency change recommendation on demo data.

## Phase 10 — MLOps

- **Entry:** can start in parallel with Phase 4 in practice, but formally
  closed out here.
- **Build:** MLflow experiment tracking wired into every training script
  (doc 07/08), DVC for datasets/artifacts, model registry conventions
  (`model_versions` table populated automatically on registration), basic
  drift monitoring hook (compare live prediction error vs. training-time
  metric on a rolling window).
- **Exit:** every model/agent in the repo has a traceable MLflow run and a
  `model_versions` row; retraining is a documented, scripted command, not a
  manual notebook process.

## Phase 11 — Final evaluation

- **Entry:** Phases 4-10 exit.
- **Build:** run the full evaluation methodology (doc 14): prediction model
  comparisons, fleet-control strategy comparisons, routing comparisons,
  stress tests, ablations.
- **Exit:** a results report exists with real numbers (no placeholder
  metrics) answering the research questions in the project's thesis framing.
